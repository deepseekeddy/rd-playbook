# 第一阶段：搭建可试跑的最小闭环

## A. 管理员：创建团队基线（30分钟）

1. 填写 `01-团队与责任台账.csv`。
2. 每人只设一个主角色，可以有一个副角色。
3. 每人必须有备份人，备份人不等于默认共同主责。
4. 把真实代码目录或业务模块填到“负责产品或目录”。
5. 默认 WIP 上限设为 2。

验收：十行均有姓名、飞书账号、GitHub 用户名、负责范围和备份人。

## B. PM：创建飞书需求主表（45分钟）

1. 新建多维表格“研发交付主表”。
2. 按 `02-飞书需求主表字段.md` 建立必需字段。
3. 只建一条试点需求，编号 `REQ-YYYY-NNN`。
4. 设置父需求 DRI、业务优先级、目标日期和下一责任人。
5. 将原始需求、PRD 草稿和相关会议链接挂到该行。

验收：打开一行即可看到该需求的业务状态、下一责任人和上游材料。

## C. GitHub 管理员：创建研发 Project（60分钟）

1. 进入 GitHub Organization 的 `Projects`，点击 `New project`。
2. 选择空白项目，命名为 `R&D Delivery`。
3. 创建字段：`Status`、`Iteration`、`Priority`、`Workstream`、`Type`、`Risk`、`Health`、`Estimate`、`Target date`。
4. `Status` 选项：`Intake / Ready / In Progress / In Review / Ready for QA / In QA / Ready for Release / Blocked / Done`。
5. 创建视图：`当前迭代`、`我的工作`、`待审核`、`负载`、`风险与阻塞`。
6. 在 `Workflows` 中开启 Auto-add，只选择试点仓库。

验收：试点 Issue 可在 Project 中看到，并能设置 Assignee、Status、Iteration 和 Target date。

## D. TL：启用标准模板（45分钟）

1. 在真实仓库新建一个普通分支。
2. 将 `github-template/.github` 中的 Issue Form 和 PR 模板复制到真实仓库的 `.github/`。
3. 将 `CODEOWNERS.example` 中的组织名、Team 和目录替换为真实值。
4. 通过 PR 提交这些模板，不直接推送主分支。
5. 在模板 PR 审核中确认责任目录是否与团队台账一致。

验收：创建 Issue 时可选 Requirement、Delivery Task、Change 和 Bug 四种表单。

## E. 全员：在 Trae 里试跑（30分钟）

1. 进入 TraeWork，选择适合自己的 Work、Design 或 Code 模式。
2. 选择飞书与 GitHub 连接，只授予试点需要的范围。
3. 复制 `03-Trae每日工作入口.md` 的第一条指令。
4. 检查 Trae 是否返回真实的 REQ-ID、Issue 和原始链接。
5. 本轮先不让 Trae 自动修改状态；等读取准确率验证通过后再开写权限。

验收：每个人都能在 Trae 里看到与自己角色相关的试点工作。

## F. 第一次试跑会（30分钟）

只确认以下问题：

- 父需求 DRI 是谁？
- 下一动作属于谁？
- 每个子任务是否只有一个 Assignee？
- PRD/TSD/Figma 的版本是否可追溯？
- 哪些工作需要 Reviewer？
- 当前阻塞的解除责任人是谁？
- 下一次状态变化将通知谁？

试跑会结束后，由 Trae 生成会议摘要，并把正式决策回写到飞书决策日志。
