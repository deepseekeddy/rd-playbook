# 代码评审

## 触发条件

- 用户提交了PR，要求AI辅助评审
- 用户说"帮我看看这个PR"、"review一下代码"、"检查这个实现"
- PR创建后自动触发评审
- 合并前需要确认代码质量

## 前置条件

1. **有明确的变更范围**：PR链接或diff
2. **有需求上下文**：关联的REQ-ID、PRD版本、TSD版本
3. **项目规则可访问**：AGENTS.md、代码规范

## 输入要求

### 必需

- PR链接或diff内容
- 关联的 REQ-ID
- PRD/TSD 版本（用于核对需求覆盖）

### 缺失处理

- 缺少REQ-ID → 提醒PR描述缺少关联需求，评审时标注"需求覆盖无法验证"
- 缺少PRD/TSD → 只做代码质量和安全评审，不做需求覆盖检查
- diff过大（>500行或>20个文件）→ 建议拆分PR，先评审核心模块

## 执行步骤

### 第1步：理解变更上下文

1. 读取PR描述，确认：
   - 关联的REQ-ID和FR-ID
   - 变更范围和目标
   - 测试证据
   - 风险和回滚说明
2. 读取相关PRD/TSD的对应章节
3. 确认变更是否在TSD授权范围内

### 第2步：需求覆盖检查

核对每个FR-ID是否有对应实现：
- FR-ID → 代码模块/函数的映射
- 是否有遗漏的功能点
- 是否有超出范围的改动（scope creep）
- 验收标准是否在代码中体现

### 第3步：正确性检查

- 逻辑是否正确，有无明显bug
- 边界条件处理（空值、零、负数、最大值、并发）
- 错误处理是否完整（不要吞异常）
- 资源释放（文件、连接、锁）
- 事务边界是否正确

### 第4步：安全与数据检查

- **权限**：是否校验了用户权限，有无越权漏洞
- **注入**：SQL注入、XSS、命令注入、路径遍历
- **PII**：个人信息是否脱敏、加密、审计
- **密钥**：有无硬编码密钥、Token、密码
- **输入校验**：所有外部输入是否校验
- **敏感操作**：删除、修改、导出等高风险操作是否有保护

### 第5步：并发与一致性

- 共享资源是否有并发保护
- 竞态条件是否存在
- 幂等性是否保证
- 缓存一致性
- 分布式事务或最终一致性处理

### 第6步：性能检查

- N+1查询
- 大循环中的低效操作
- 不必要的全表扫描
- 内存泄漏风险
- 大文件/大数据量处理
- 同步调用是否可能阻塞

### 第7步：可观测性

- 关键路径是否有日志
- 日志是否包含必要上下文（REQ-ID、用户ID、操作）
- 是否有敏感信息泄露到日志
- 关键指标是否埋点
- 错误是否可追踪（trace ID）

### 第8步：测试充分性

- 新增代码是否有对应测试
- 测试是否覆盖了正常、异常、边界场景
- 测试是否真正验证了行为（不是只跑通）
- 有无测试跳过或mock过度
- 如可执行，运行最小相关测试并记录结果

### 第9步：可维护性

- 命名是否清晰
- 函数/类是否单一职责
- 是否有重复代码
- 注释是否准确（不要注释"是什么"，要注释"为什么"）
- 是否符合项目代码规范
- 有无遗留的待办标记、调试代码或注释掉的代码

### 第10步：兼容性与迁移

- 接口变更是否向后兼容
- 数据库变更是否有迁移脚本
- 配置变更是否有默认值
- 灰度发布是否支持
- 回滚是否可行

## 问题分级

每个问题必须标注级别：

| 级别 | 定义 | 处理要求 |
|---|---|---|
| **P0 阻塞** | 安全漏洞、数据丢失、核心功能错误、生产风险 | 必须修复，不可合并 |
| **P1 重要** | 逻辑缺陷、性能问题、测试缺失、边界未处理 | 应修复，修复后可合并 |
| **P2 建议** | 代码质量、可维护性、命名、优化建议 | 可合并，但建议跟进 |
| **P3 备注** | 风格、文档、微小改进 | 不阻塞，可选改进 |

每个问题必须包含：
- 文件路径和行号
- 问题描述
- 可复现条件或影响
- 修复建议（具体到代码级）

## 测试证据验证

- **已运行**：列出实际运行的测试命令和结果
- **未运行**：明确标注"未执行"，说明原因
- **无法运行**：说明环境或依赖问题
- **不得声称测试通过**，除非有实际执行证据

## 输出格式

```
## 评审总结

- PR：[链接]
- REQ-ID：REQ-YYYY-NNN
- 变更规模：X个文件，+XXX/-XXX行
- 需求覆盖：完整 / 部分（说明缺失） / 无法验证

## 阻塞问题（P0）

### P0-1：[问题标题]
- 位置：`path/to/file.js:42`
- 问题：[描述]
- 影响：[后果]
- 复现：[步骤]
- 建议：[修复方案]

## 重要问题（P1）

### P1-1：...

## 建议改进（P2）

### P2-1：...

## 测试证据

| 测试 | 状态 | 结果 |
|---|---|---|
| 单元测试 | 已运行 | 120 passed |
| 集成测试 | 未运行 | 缺少测试环境 |
| Lint | 已运行 | passed |

## 残余风险

- [列出即使修复后仍存在的风险]

## 评审结论

- [ ] Approve — 可以合并
- [ ] Request changes — 需修复P0/P1后重新评审
- [ ] Comment — 有建议但不阻塞
```

## 完成定义

- 所有P0问题有明确修复方案
- 需求覆盖已验证或明确标注无法验证
- 测试状态如实记录
- 评审结论明确（Approve / Request changes / Comment）
- 没有把纯风格偏好当成缺陷

## 禁止行为

- 不得在未读代码的情况下给出"看起来没问题"
- 不得伪造测试结果
- 不得把个人编码风格偏好当成P0/P1问题
- 不得建议大规模重构超出当前PR范围
- 不得批准自己提交的代码（AI辅助评审不能代替真人Reviewer）
- 不得忽略安全问题（PII、权限、注入）
- 不得在diff不完整的情况下声称评审完成

## 与其他Skill的协作

- 上游：`tsd-authoring`（技术方案）、`implementation-planning`（任务拆分）
- 下游：`test-acceptance`（测试验收）、`release-readiness`（发布检查）

## 评审检查清单（快速版）

每次评审至少过一遍：
- [ ] REQ-ID/FR-ID 关联完整
- [ ] 需求无遗漏、无越界
- [ ] 无安全漏洞（权限/注入/PII/密钥）
- [ ] 错误处理完整
- [ ] 边界条件处理
- [ ] 并发与幂等
- [ ] 测试覆盖核心路径
- [ ] 日志与指标
- [ ] 兼容性与回滚
- [ ] 无调试代码和硬编码
