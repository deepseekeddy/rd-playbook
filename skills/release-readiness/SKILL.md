# 发布就绪检查

## 触发条件

- 需求开发测试完成，准备发布
- 用户说"做个发布检查"、"能不能上线"、"Go/No-Go"
- 发布前需要生成发布单和变更说明
- 紧急修复需要快速发布

## 前置条件

1. **代码已合并**：所有相关PR已合并到发布分支
2. **测试已完成**：QA验收通过，P0/P1缺陷清零
3. **制品已构建**：不可变制品已生成并通过CI
4. **发布模板可用**：使用 [assets/release-template.md](assets/release-template.md)

## 输入要求

### 必需

- 关联的 REQ-ID 列表
- 目标版本号（如 v2.8.0）
- 发布环境（staging/production）
- 制品链接或构建号
- 测试报告链接

### 缺失处理

- 缺少测试报告 → 结论必须为 NO-GO，标注"测试证据缺失"
- 缺少制品 → 结论必须为 NO-GO
- 缺少回滚方案 → 结论必须为 NO-GO
- 非关键信息缺失 → 标注"待补充"，不阻塞但需在发布前补齐

## 执行步骤

### 第1步：核对版本与范围

1. 确认本次发布包含的 REQ-ID 和变更清单
2. 确认版本号符合语义化版本规范
3. 确认变更范围与发布计划一致，有无意外包含的变更
4. 确认所有变更都有对应的PR和评审记录

### 第2步：代码与制品检查

- [ ] 所有PR已合并，无未合并的依赖
- [ ] 主干分支保护规则通过
- [ ] CI全部通过（lint、test、build、security scan）
- [ ] 制品不可变，有唯一标识（commit SHA + build号）
- [ ] 制品已在staging环境验证通过
- [ ] 漏洞扫描无高危漏洞
- [ ] 许可证合规检查通过

### 第3步：测试与质量检查

- [ ] 单元测试通过率 ≥ 阈值（如90%）
- [ ] 集成测试通过
- [ ] QA验收通过，P0/P1缺陷清零
- [ ] 回归测试通过
- [ ] 性能测试达标（如涉及性能变更）
- [ ] 安全测试通过（如涉及安全变更）
- [ ] 兼容性测试通过（如涉及兼容性变更）
- [ ] 测试覆盖率无明显下降

### 第4步：数据库与配置检查

- [ ] 数据库迁移脚本已准备，可重复执行
- [ ] 迁移兼容旧版本（expand/migrate/contract）
- [ ] 迁移有回滚脚本
- [ ] 配置与代码分离，配置已更新到目标环境
- [ ] 密钥/凭证已配置到目标环境（不硬编码）
- [ ] Feature Flag已设置（如使用灰度发布）
- [ ] 数据备份已完成或已确认可恢复

### 第5步：监控与告警检查

- [ ] 关键业务指标有监控
- [ ] 错误率、延迟、饱和度有告警
- [ ] 新增功能有对应埋点和指标
- [ ] 告警通知到人（不是只发到无人看的渠道）
- [ ] 仪表盘已更新，能看到本次发布的影响
- [ ] 日志级别合适，无敏感信息泄露

### 第6步：发布计划检查

- [ ] 发布窗口明确（时间、时长）
- [ ] 发布步骤清晰，执行人明确
- [ ] 灰度策略明确（比例、观察周期、晋级条件）
- [ ] 值守人员明确（发布期间和发布后观察窗）
- [ ] 通知计划明确（谁需要知道发布，什么时候通知）
- [ ] 依赖服务已确认可支持本次发布

### 第7步：回滚方案检查

- [ ] 回滚触发条件明确（错误率>X%、延迟>Yms、核心功能不可用）
- [ ] 回滚步骤清晰，可在RTO内完成
- [ ] 回滚已演练或有明确操作手册
- [ ] 数据回滚方案明确（迁移回退、数据恢复）
- [ ] 回滚后功能降级方案明确
- [ ] 回滚决策人明确（谁有权决定回滚）

### 第8步：沟通与文档

- [ ] 发布说明（Release Notes）已编写，面向用户和内部
- [ ] 变更单已创建并获批
- [ ] 相关团队已通知（客服、运营、销售）
- [ ] 客户沟通已准备（如涉及客户可见变更）
- [ ] 运维手册/Runbook已更新
- [ ] 已知问题和限制已记录

### 第9步：生成发布单

使用 [assets/release-template.md](assets/release-template.md) 生成发布单，包含所有检查结果和证据链接。

### 第10步：给出结论

根据检查结果给出三选一结论：

| 结论 | 条件 |
|---|---|
| **GO** | 所有必检项通过，无P0风险，回滚可行 |
| **CONDITIONAL GO** | 有非阻塞项待补齐，但有明确负责人和时间，风险可控 |
| **NO-GO** | 有P0未解决、回滚不可行、无监控、无授权审批、测试证据缺失 |

## 输出格式

使用 [assets/release-template.md](assets/release-template.md) 生成发布单，核心结构：

```
# 发布单 vX.Y.Z

## 基本信息
- REQ-ID：[列表]
- 版本：vX.Y.Z
- 环境：production
- 发布时间：[日期时间]
- 执行人：[姓名]
- 审批人：[姓名]

## 变更摘要
[本次发布的主要变更]

## 检查清单

### 代码与制品
- [x] CI通过 — [链接]
- [x] 制品构建 — [链接]
- [ ] 漏洞扫描 — [结果]

### 测试与质量
...

### 数据库与配置
...

### 监控与告警
...

### 发布计划
...

### 回滚方案
...

## 风险与缓解
| 风险 | 等级 | 缓解措施 |
|---|---|---|

## 结论
GO / CONDITIONAL GO / NO-GO

理由：[说明]

## 审批
- TL：[签字]
- SRE：[签字]
- PM：[签字]（如涉及客户可见变更）
```

## 完成定义

- 所有必检项有明确结果（通过/不通过/不适用）
- 每个不通过项有负责人和修复计划
- 回滚方案具体可执行
- 结论明确（GO/CONDITIONAL GO/NO-GO）
- 发布单有真实证据链接，不是空勾选
- 生产操作必须由授权人员确认，AI不得代替审批

## 禁止行为

- 不得在测试证据缺失时给出GO
- 不得伪造CI结果、测试报告或审批签名
- 不得跳过回滚方案检查
- 不得把"应该没问题"当成风险评估
- 不得在无监控的情况下发布
- 不得建议AI自动执行生产部署
- 不得忽略数据库迁移的回滚可行性
- 不得在未通知相关团队的情况下发布客户可见变更

## 红线（触发即NO-GO）

以下任何一条不满足，结论必须是NO-GO：
1. P0缺陷未关闭
2. CI检查未通过
3. 回滚方案不可行或未演练
4. 无监控或告警
5. 无授权审批
6. 数据库迁移不可逆
7. 安全扫描有高危漏洞
8. 制品与代码版本不对应

## 与其他Skill的协作

- 上游：`test-acceptance`（测试验收）、`code-review`（代码评审）
- 下游：`operate-observe`（上线观测）
- 关联：`delivery-orchestrator`（交付编排）

## 发布后检查清单

发布完成后立即执行：
- [ ] 冒烟测试通过
- [ ] 错误率无异常上升
- [ ] 延迟无异常上升
- [ ] 核心业务流程正常
- [ ] 数据库迁移成功
- [ ] 配置生效
- [ ] 日志无异常报错
- [ ] 进入观察窗，值守人员到位
