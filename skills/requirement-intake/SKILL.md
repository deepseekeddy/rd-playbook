# 需求澄清与分诊

## 触发条件

- 用户提供了一段客户反馈、销售转述、用户抱怨或业务想法，需要结构化
- 用户说"帮我整理一下这个需求"、"这个能不能做"、"评估一下"
- 飞书需求表中新增了一条信息不完整的记录，需要补全
- 需求评审前需要确认问题定义和范围

## 输入要求

### 必需信息（缺失时必须追问，不得编造）

1. **来源**：谁提出的？客户名称/销售/内部团队/用户反馈渠道
2. **原始描述**：用户的原话或原始记录，不要转述
3. **当前现状**：用户现在是怎么做的？痛点是什么？
4. **期望结果**：用户希望达到什么效果？

### 补充信息（有则更好，没有则标记待确认）

- 期望时间、预算约束、涉及的系统或模块
- 是否有竞品参考、截图或示例
- 影响的用户量或频率

### 缺失信息处理

按以下优先级追问，一次最多问3个问题：

1. 如果没有原始描述 → 要求用户粘贴原话或截图
2. 如果没有明确用户/场景 → 问"谁在什么情况下遇到这个问题"
3. 如果没有期望结果 → 问"你希望最终变成什么样"
4. 其他缺失项标记为"待确认"，不阻塞输出草稿

## 执行步骤

### 第1步：提取事实与假设

从原始描述中分离：
- **事实**：用户明确说的、可验证的信息
- **假设**：你根据上下文推断的，必须标注"假设"
- **方案**：用户提出的解决方案（不要当成问题本身）
- **约束**：时间、预算、技术、合规等限制

### 第2步：定义问题陈述

用一句话写清：**谁**在**什么场景**下遇到**什么问题**，导致**什么影响**。

模板：
```
[用户角色] 在 [场景] 时，因为 [根本原因]，无法 [期望动作]，导致 [业务影响]。
```

### 第3步：评估价值与优先级

从三个维度评估：
- **用户价值**：解决了多少用户的什么痛点？频率多高？
- **业务价值**：对收入、留存、效率、成本的影响？
- **紧迫性**：是否有截止日期、客户承诺、合规要求？

给出建议优先级（P0/P1/P2/P3）和理由。P0=阻塞客户使用或收入；P1=重要客户需求或高频痛点；P2=有价值但可延后；P3=锦上添花。

### 第4步：界定范围

- **In scope**：本次要解决的具体问题
- **Out of scope**：明确不做的相关需求（避免范围蔓延）
- **依赖**：需要哪些团队、系统、数据或决策支持
- **风险**：技术风险、合规风险、用户接受度风险

### 第5步：定义成功指标

每个需求至少一个可量化指标：
- 指标名称、定义、公式
- 当前基线（未知则标记"待测量"）
- 目标值
- 数据来源
- 观察周期（如发布后2周）

### 第6步：生成 REQ-ID 占位符并建议 DRI

- 生成 `REQ-YYYY-NNN` 格式的占位编号（实际编号由飞书表自动分配）
- 根据需求类型建议 DRI 角色：产品类→PM，技术类→TL，运营类→对应负责人
- 建议下一步动作：进入PRD / 补充调研 / 拒绝 / 合并到已有需求

## 完成定义

评审者能独立回答以下问题，无需追问：
1. 为什么做？（问题和价值）
2. 为谁做？（用户和场景）
3. 成功是什么？（可量化指标）
4. 先不做什么？（明确的范围边界）
5. 谁来负责？（DRI和下一步）

## 禁止行为

- 不得把用户提出的解决方案当成问题本身
- 不得编造业务数据、用户量、收入影响
- 不得自行决定优先级为P0（P0必须由PM或负责人确认）
- 不得跳过原始描述直接写需求
- 不得在未确认的情况下创建飞书需求记录（先输出草稿，经用户确认后再写入）
- 不得伪造 REQ-ID（实际编号由飞书表分配）

## 示例

### 输入
> "客户A说他们的运营每天要手动导出订单数据，每次要选半天条件，还经常导出失败，能不能优化一下？"

### 输出（关键部分）
```
## 问题陈述
客户A的运营人员 在批量导出订单数据 时，因为导出条件选择繁琐且导出不稳定，无法高效获取订单数据，导致运营效率低且数据不可靠。

## 目标与成功指标
| 指标 | 定义 | 基线 | 目标 | 数据源 |
|---|---|---|---|---|
| 导出操作时长 | 从开始选择到下载完成 | 待测量（预估>5分钟） | <2分钟 | 前端埋点 |
| 导出失败率 | 导出任务失败/总导出 | 待测量 | <1% | 后端日志 |

## 建议优先级
P1 — 重要客户高频痛点，影响运营效率，但不阻塞核心流程。

## 分诊结论
- 建议 DRI：PM
- 下一步：进入PRD，需补充当前导出量、失败原因调研
- 建议 REQ-ID：REQ-2026-043（占位）
```
