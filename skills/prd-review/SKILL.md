# PRD 评审

## 触发条件

- PM 完成PRD草稿，要求进行结构化评审
- 用户说"帮我评审PRD"、"检查需求文档"、"看看有没有遗漏"
- PRD状态从 Draft 即将流转到 Approved 之前
- 需求发生变更，需要评估变更对PRD的影响
- TL 或 QA 在设计/TSD编写前主动检查PRD完备性

## 前置条件

1. **PRD文档可访问**：飞书文档链接或本地 Markdown 文件
2. **关联 REQ-ID 明确**：PRD头部包含关联的 REQ-ID 和上游文档
3. **评审角色可分配**：至少能从产品（PM）、设计、研发（TL）、测试（QA）四个视角展开

如果PRD缺少 REQ-ID 或处于未分诊状态，先调用 `requirement-intake` 完成分诊，再调用 `prd-authoring` 补齐PRD。

## 输入要求

### 必需

- PRD 文档链接或完整内容
- 关联的 REQ-ID
- PRD 版本号（用于标注评审基线）

### 缺失处理

- 缺少REQ-ID → 标注"需求关联无法验证"，提醒PM补充后重新评审
- 缺少PRD版本号 → 以评审日期作为基线，标注"版本号待补"
- 缺少上游文档 → 只做内部一致性检查，不做上下文追溯
- 缺少设计/研发/测试任一视角的上下文 → 标注该视角为"待补充"，不做该视角深度检查

## 执行步骤

### 第1步：读取PRD上下文

1. 读取PRD全文，确认头部信息（状态、Owner、评审人、版本、REQ-ID、上游文档）
2. 读取关联的需求分诊记录，确认问题陈述和目标
3. 读取产品文档集中的相关业务规则、术语口径
4. 如有类似需求的历史PRD，读取作为参照基线

### 第2步：产品视角评审（PM）

从产品价值和需求完整性角度检查：

- **价值与指标**：问题陈述是否清晰；成功指标是否可量化、可埋点
- **目标与非目标**：范围是否明确划定，非目标是否列出以防 scope creep
- **用户画像**：角色、技术水平、使用频率是否定义
- **核心场景**：首次使用、日常使用、能力发现三条路径是否覆盖
- **用户旅程**：每条路径是否完整（从触发到成功终点），异常分支是否列出
- **优先级**：FR-ID 的优先级是否标注，是否与业务价值匹配

### 第3步：设计视角评审

从交互和视觉可行性角度检查：

- **功能覆盖**：每个FR是否包含足够的交互细节供设计展开
- **状态矩阵**：空白态、输入态、加载态、错误态、折叠态是否定义
- **权限差异**：不同角色（普通用户/白名单用户）的界面差异是否说明
- **边界数据**：空列表、超长文本、无图、大数据量的展示规则是否定义
- **响应式线索**：移动端与桌面端的布局差异是否有方向性描述
- **文案**：按钮、提示、空状态文案是否给出，或标注"待设计补充"

### 第4步：研发视角评审（TL）

从技术可行性和实现成本角度检查：

- **接口可行性**：依赖的外部API是否已确认可用，字段是否匹配
- **数据模型**：需要的数据字段是否定义，是否需要新建表或扩展
- **非功能需求**：性能指标是否合理且可测，安全要求是否明确
- **埋点**：每个成功指标是否有对应埋点事件，属性是否足够
- **依赖**：外部依赖是否列出，是否有降级方案
- **风险**：技术风险是否识别，等级是否合理
- **实现拆分**：FR粒度是否适合拆分为独立任务，是否有粒度过大需拆分的

### 第5步：测试视角评审（QA）

从可测试性和验收角度检查：

- **验收标准格式**：每个FR是否用 Given/When/Then 格式
- **场景覆盖**：正常流程、空数据、错误、权限、边界值是否覆盖
- **可测试性**：每条验收标准是否可通过具体操作验证（不是模糊描述）
- **异常处理**：异常矩阵中的每项是否有明确的处理方式和用户提示
- **非功能可测**：性能、兼容性、可访问性指标是否给出具体数值或标准
- **埋点可验证**：埋点事件是否可通过抓包或日志验证

### 第6步：跨视角一致性检查

检查四个视角之间的交叉一致性：

- **FR-ID 对齐**：用户旅程中的每一步是否映射到对应FR-ID
- **状态矩阵对应设计**：状态矩阵中的每个状态是否有对应的设计交付要求
- **异常处理对应测试**：异常矩阵中的每项是否有对应的验收标准
- **埋点对应指标**：每个成功指标是否能通过埋点数据计算
- **依赖对应风险**：每个依赖是否有对应的风险项和缓解措施
- **权限矩阵对应FR**：权限矩阵中的每个角色差异是否有对应FR描述

### 第7步：变更影响评估（如适用）

如果PRD是因需求变更而更新：

- 对照变更记录，确认变更涉及的所有FR已更新
- 检查变更是否引入新的依赖、风险或非功能要求
- 评估变更对已有验收标准的影响，是否有需废弃或新增的
- 检查版本号是否已递增，变更记录是否已添加

### 第8步：输出评审报告并请求确认

输出完整评审报告，明确标注：
- 所有 Blocker 问题（必须修复后才能进入下一阶段）
- 所有 Major 问题（高概率返工或漏测，应修复）
- 所有 Minor 问题（可优化，不阻塞）
- 审批结论和建议的下一步

**未经用户确认，不得将PRD状态改为 Approved 或更新需求表状态。**

## 问题分级

每个问题必须标注级别：

| 级别 | 定义 | 处理要求 |
|---|---|---|
| **Blocker** | 需求不可实现、核心逻辑矛盾、关键验收标准缺失、无法进入设计或TSD | 必须修复，不可流转 |
| **Major** | 高概率返工或漏测、边界未覆盖、埋点缺失、非功能指标模糊 | 应修复，修复后可流转 |
| **Minor** | 文案优化、格式规范、建议性改进 | 可流转，建议跟进 |

每条问题必须包含：
- 位置（章节号或FR-ID）
- 问题描述
- 影响（对设计/研发/测试的具体后果）
- 修复建议（具体到PRD层级）
- Owner（PM/设计/TL/QA）

## 完成定义

- 所有Blocker问题有明确修复方案和Owner
- 四视角检查清单全部填写（Pass或Fail）
- 评审结论明确（Approved / Approved with actions / Rejected）
- 必须完成项和可延后项已列出，附限期
- 重新评审触发条件已定义
- 没有把纯格式偏好当成Blocker

## 禁止行为

- 不得仅做文字润色而不检查需求一致性
- 不得在未读PRD全文的情况下给出"看起来没问题"
- 不得跳过任一视角的检查（产品/设计/研发/测试缺一不可）
- 不得把设计决策（布局、配色）作为PRD的Blocker（那是Figma的事）
- 不得把技术实现方案写进评审建议（那是TSD的事）
- 不得在缺少Blocker证据时标记Approved
- 不得伪造评审人签名或批准状态
- 不得把个人写作风格偏好当成Major问题

## 与其他Skill的协作

- 上游：`prd-authoring`（PRD编写），`requirement-intake`（需求分诊）
- 下游：`figma-handoff`（设计交付检查），`tsd-authoring`（技术方案编写）
- 并行：`code-review`（代码评审，评审标准参考）
- 变更：需求变更后先更新PRD版本号，再重新执行本评审

## 评审检查清单（快速版）

每次评审至少过一遍：
- [ ] REQ-ID 关联完整
- [ ] 价值与成功指标可量化
- [ ] 目标与非目标范围清晰
- [ ] 用户旅程覆盖三条核心路径
- [ ] 每个FR有Given/When/Then验收标准
- [ ] 状态矩阵覆盖所有页面状态
- [ ] 异常处理矩阵完整
- [ ] 权限矩阵覆盖所有角色差异
- [ ] 非功能需求有具体数值
- [ ] 埋点事件与指标对齐
- [ ] 依赖与风险有缓解措施
- [ ] 无未决项被遗漏

## 示例

### Blocker 示例

```
### B-1：FR-04 验收标准缺失错误态场景
- 位置：FR-REQ-2026-001-04 对话输入区
- 问题：验收标准只覆盖了正常发送和空输入禁用，缺少文件上传超限和网络断开两个错误态场景
- 影响：QA无法生成文件超限和断网场景的测试用例；开发可能遗漏前端拦截逻辑
- 建议：补充两条验收标准：
  - Given 上传超过10M的图片 When 选择文件 Then 前端提示"文件大小超限"
  - Given 网络断开 When 查看输入区 Then 输入区禁用并提示"网络连接异常"
- Owner：PM
```

### Major 示例

```
### M-1：成功指标缺少对应埋点
- 位置：二、目标与非目标 / 八、数据与埋点
- 问题：目标2"用户登录后30秒内可完成首次AI交互"缺少对应埋点事件
- 影响：无法通过数据验证目标是否达成，上线后无法评估效果
- 建议：新增埋点事件 first_interaction，属性包含 user_id、time_to_first_action（从page_view到首次chat_send的秒差）
- Owner：PM
```

### Minor 示例

```
### m-1：FR-03 副标题文案建议精简
- 位置：FR-REQ-2026-001-03 Hero标题区
- 问题：副标题"释放创意生产力，实现视觉创作、专业翻译与协同办公一体化"较长，移动端可能截断
- 建议：考虑提供短版本备选，如"创意·翻译·协同，一站搞定"，待设计确认
- Owner：PM
```
