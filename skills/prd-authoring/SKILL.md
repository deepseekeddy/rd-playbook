# PRD 编写

## 触发条件

- 需求已通过分诊（状态为 Triaged），用户要求编写PRD
- 用户说"帮我写PRD"、"出个需求文档"、"把这个需求整理成文档"
- 已有PRD需要根据变更单更新
- 需求评审后需要修订PRD

## 前置条件（不满足则先追问）

1. **需求已分诊**：有明确的问题陈述、目标用户、成功指标和范围
2. **PRD模板可用**：使用 [assets/prd-template.md](assets/prd-template.md)
3. **产品文档集可访问**：能读取产品术语、业务规则、指标口径

如果需求未分诊，先调用 `requirement-intake` 完成分诊。

## 输入要求

### 必需

- 需求主记录链接或 REQ-ID
- 已分诊的需求摘要（问题、用户、目标、范围）
- 相关的产品术语和业务规则文档

### 缺失处理

- 缺少业务规则 → 列出假设，标注"待PM确认"
- 缺少指标口径 → 从产品文档集查找，找不到则标记"待定义"
- 缺少用户旅程细节 → 给出合理默认，标注"待验证"
- 核心信息缺失超过3项 → 暂停输出，先追问PM

## 执行步骤

### 第1步：读取上下文

1. 读取需求主记录，确认状态为 Triaged 或 PRD Draft
2. 读取产品文档集中的相关术语、业务规则、指标口径
3. 读取PRD模板
4. 如有类似需求，读取已有PRD作为参考

### 第2步：构建用户旅程

按时间线梳理用户从触发需求到完成目标的完整路径：
- 触发场景：用户在什么情况下开始使用
- 关键步骤：每一步用户做什么、系统做什么
- 异常分支：每一步可能出什么错、如何处理
- 成功终点：用户达到什么状态算完成

每个步骤标注对应的功能点（后续分配FR-ID）。

### 第3步：编写功能需求（FR-ID）

每个功能点分配唯一 `FR-ID`，格式：`FR-REQ-XXXX-NN`（如 FR-2026-042-01）。

每个FR必须包含：
- **名称**：简短动词短语
- **用户故事**：作为[角色]，我希望[功能]，以便[价值]
- **描述**：具体做什么
- **业务规则**：相关的计算、判断、限制规则
- **验收标准**：Given/When/Then 格式，覆盖正常、空、错误、权限、边界场景

### 第4步：定义状态与异常矩阵

列出所有关键实体的状态流转：
- 状态列表：每个实体有哪些状态
- 状态迁移：什么触发从A到B
- 异常处理：每个状态下可能的异常和恢复方式
- 权限差异：不同角色看到的状态和可执行操作

### 第5步：非功能需求

至少覆盖：
- **性能**：响应时间、并发量、数据量上限
- **安全与隐私**：权限控制、数据脱敏、审计要求
- **兼容性**：浏览器/设备/系统版本
- **可访问性**：键盘操作、屏幕阅读器、对比度
- **国际化**：多语言、时区、货币（如需要）

### 第6步：数据与埋点

- 需要新增或修改的数据字段
- 埋点事件：事件名、触发时机、属性、用途
- 指标关联：每个成功指标对应哪些埋点

### 第7步：依赖、风险与发布

- 依赖：其他团队、系统、第三方服务
- 风险：技术风险、用户接受度、合规风险
- 发布策略：灰度、全量、特性开关
- 运营要求：上线后需要什么运营动作

### 第8步：输出草稿并请求确认

先输出完整PRD草稿，明确标注：
- 所有假设和待确认项
- 不确定的业务规则
- 需要PM/设计/TL/QA分别确认的部分

**未经用户确认，不得创建飞书文档或更新需求表状态。**

## 输出格式

使用 [assets/prd-template.md](assets/prd-template.md) 骨架，正文首部必须包含：

```
状态：Draft
Owner：[PM姓名]
评审人：设计、TL、QA
版本：v0.1
目标版本：[如v2.8.0]
关联 REQ-ID：REQ-YYYY-NNN
最后更新：[日期]
```

功能需求部分每个FR的格式：

```
### FR-REQ-XXXX-NN：[功能名称]

**用户故事**：作为[角色]，我希望[功能]，以便[价值]。

**描述**：[具体说明]

**业务规则**：
1. [规则1]
2. [规则2]

**验收标准**：
- Given [前置条件] When [操作] Then [预期结果]
- Given [空数据] When [操作] Then [空状态提示]
- Given [无权限用户] When [操作] Then [拒绝并提示]
- Given [边界值] When [操作] Then [正确处理]
```

## 完成定义

- PM 能据此确认需求范围和业务规则
- 设计能据此完成交互和视觉
- TL 能据此做技术方案和估算
- QA 能据此生成测试用例
- 每个FR都有可测试的验收标准
- 所有假设和待确认项都明确标注

## 禁止行为

- 不得编造业务规则、数据口径、用户量
- 不得把技术实现细节写进PRD（那是TSD的事）
- 不得把设计决策（具体布局、配色）写进PRD（那是Figma的事）
- 不得在未确认的情况下将PRD状态设为Approved
- 不得跳过验收标准直接写功能描述
- 不得伪造评审人签名或批准状态
- 不得在PRD中包含"最终版"、"最终版2"等非版本号表述

## 与其他Skill的协作

- 上游：`requirement-intake`（需求分诊）
- 评审：`prd-review`（PRD结构化评审）
- 下游：`figma-handoff`（设计交付）、`tsd-authoring`（技术方案）
- 变更：需求变更需先创建变更记录，再更新PRD版本号

## 示例

### FR示例

```
### FR-REQ-2026-042-01：创建导出任务

**用户故事**：作为运营人员，我希望选择导出条件后创建异步导出任务，以便在后台处理大量订单数据。

**描述**：用户在订单列表页选择筛选条件，点击"导出"，系统创建异步导出任务并返回任务ID。用户可在导出记录页查看任务状态和下载结果。

**业务规则**：
1. 单次导出最大行数为100,000行，超出时提示缩小筛选范围
2. 同一用户同时最多有3个进行中的导出任务
3. 导出文件保留24小时后自动删除
4. 导出字段受用户权限控制，无权限字段不可选

**验收标准**：
- Given 已选择有效筛选条件 When 点击导出 Then 创建导出任务并显示"导出中"状态
- Given 筛选结果超过100,000行 When 点击导出 Then 提示"导出数据量过大，请缩小筛选范围"
- Given 用户已有3个进行中任务 When 点击导出 Then 提示"同时最多3个导出任务，请等待完成"
- Given 无权限用户 When 查看导出字段列表 Then 不显示无权限字段
```
